# 场地内通用导航：设计文档（任何手机、不依赖 AR）

状态：草案，2026-10-24。依据本仓库已有的实测与回放结果（见第 5 节，每个数字都给出处），没有新增实验。

---

## 1. 目标与结论

**目标**：顾客用自己的手机（任何品牌、任何型号，不要求 LiDAR、不要求 ARKit/ARCore）在场地里找到商品，看到「我在哪」和「怎么走」。

**结论**：顾客版不能照搬地磁定位页的方案。地磁页面靠 带 LiDAR 的 iPhone 的 ARKit 视觉里程计和逐个场地建好的磁场图，这两样在顾客手机上都不能假设。顾客版的主干改为：

| 层 | 作用 | 是否必需 |
|---|---|---|
| **L1 惯导推算（PDR）+ 地图约束** | 连续跟踪：计步、步长、陀螺航向，用通道和货架约束粒子 | 必需，所有平台 |
| **L2 蓝牙标签绝对位置** | 每秒给一次「人在这片标签附近」，消除 PDR 累积漂移；冷启动 | 必需（原生 App、小程序）；网页做不到 |
| **L3 一键校准（摄像头扫黄标签 / 二维码、手机贴标签、长按地图）** | 用户主动给一个确定位置，冷启动或明显跑偏时用 | 可选，强烈建议提供 |
| **L4 增强：地磁指纹、ARKit/ARCore 视觉里程计** | 手机和场地条件允许时提高精度 | 可选，默认关 |

关键判断：

1. **标签是场地里已经存在的、密度足够的信标网**。标签位置表覆盖了绝大多数标签的位置（`docs/roadmap.md`「标签位置表」），不用装任何新硬件，也不用逐个场地采集指纹。
2. **地磁不能当主干**。同一处两次采集，磁场整体水平差 10～16 µT，跨会话中位误差 3～8 m；公开商场数据上冷启动 96% 以上错定（第 5 节）。它只适合作为「已定到之后」的增强。
3. **PDR 单独会漂，但有标签和通道约束就够用**：标签每秒给一个误差 2～3 m 量级、不累积的观测，通道约束把横向误差压在通道宽度以内，PDR 负责把两次观测之间连起来、给出朝向。
4. **网页版做不了蓝牙扫描**，只能做到「扫码定起点 + PDR + 地图约束 + 随时重新扫码」。原生 App 或小程序才有完整能力（第 4 节）。

## 2. 总体架构

```
            ┌──────────────────────── 云端（已有：server/telemetry + hpass-build） ───────────────────────┐
            │  场地地图包：地图 JSON（货架/通道）+ 标签位置表 + 可选磁场图 + 可选视觉地图，zlib 压缩      │
            │  版本 = 生成时间；手机按场地下载一次，之后离线定位                                          │
            └─────────────────────────────────────────────┬───────────────────────────────────────────────┘
                                                          │ 进店时下载（约 0.1～1 MB）
┌─────────────────────────────── 手机（定位全部在本机算） ─┴──────────────────────────────────────────────┐
│                                                                                                        │
│  传感器适配层（每个平台一份）            定位核心（平台无关，一份逻辑）            导航与界面              │
│  ─────────────────────────              ──────────────────────────────            ──────────────          │
│  加速度 / 陀螺 ───────────→ PDR：计步、步长、航向 ─┐                                                   │
│  BLE 广播（公司 ID 13）───→ 标签过滤 → 距离范围约束 ─┼→ 粒子滤波（地图约束：可走区域 + 通道）→ 位置 + 不确定度 │
│  摄像头（扫码 / OCR）────→ 校准观测（确定位置）  ─┤                │                                    │
│  长按地图 / 贴标签 ──────→ 校准观测             ─┤                ↓                                    │
│  [可选] 磁力计 ──────────→ 地磁似然（已定到后）  ─┤          路径规划（A* + 网格兜底）→ 转向提示          │
│  [可选] ARKit/ARCore ────→ 替代 PDR 的运动模型  ─┘          偏离 3 m 连续 3 次 → 重算路线               │
│                                                                                                        │
└────────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

设计原则：

- **一份定位核心，多个传感器适配层**。核心只接受统一的观测：`步(长度, 航向变化)`、`标签读数(id, rssi, t)`、`确定位置(x, y, 半径)`、可选 `磁场特征`、可选 `相对位移`。平台差异全部关在适配层里。
- **任何一层缺失都能降级运行**，界面上明确显示当前精度档位，而不是给一个看起来很准的错位置（沿用 `BLEAssist` 的思路：对不上就显示「定位中」）。
- **定位在本机算，不需要一直联网**，和现有云端地图包的做法一致（`docs/roadmap.md`「云端地图」）。

## 3. 各层设计

### L1 惯导推算 + 地图约束（主干）

复用 `HPASSKit/Fusion`：互补滤波姿态（`FusionAttitude`）、峰谷计步（`FusionStepDetector`）、Weinberg 步长、持握分类（`HoldClassifier`）、通道约束（`FusionCorridorMap` / `CorridorLock`）。

- **航向只靠陀螺积分**，不默认用罗盘（钢货架旁罗盘常偏几十度，见 `docs/sensor-audit-and-options.md`）。罗盘只在冷启动时给一个粗朝向，配合云端算出的地图朝向（`MapBearingEstimator`，F1 场地 318°）。
- **步长比例是滤波状态**，由标签观测在线校正，顾客不用做任何标定。
- **地图约束**：粒子穿过实体货架即淘汰；只用标准货架当实物，虚拟货架等非实体不当障碍（`ShelfClassifier`）。
- **持握方式**：手持看屏是主场景；放进口袋或推车时计步会失真，检测到后提示「精度下降」，不硬给位置（`CMMotionActivity` / Android Activity Recognition 只做提示）。

### L2 标签蓝牙绝对位置（主要校正源）

复用：标签过滤（公司 ID 13，厂商数据取前 4 字节为 ID，`TagParser`）、位置表（`TagLocations`，通道 + 段 → 货架）、按 RSSI 的距离范围约束（`TagRangeFix`，用实测的 P90 范围）、`BLEAssist` 的交叉检验。

- **不做指纹采集**。只用位置表：表给出每个标签在哪段货架，RSSI 只用来判断「近 / 中 / 远」，作为粒子的范围约束。实测只用表比采集学到的还准（第 5 节）。
- **过滤**：只认名单里的标签；「到哪儿都听得到」（强信号位置标准差 > 15 m）的不当标签；学到的位置和表差 > 10 m 且读数 ≥ 5 次时，以学到的为准并上报，供场地核对标签是否挪了。
- **跨机型 RSSI**：每台手机的天线和芯片不同。不要求顾客标定，用盲标定（最近 120 秒数据估计偏移，`RSSICalibrator`）在线收敛；同时按机型维护一张默认偏移表（`tools/calibrate.py` 的输出），新机型先用 0。
- **冷启动**：站着几秒，标签给出位置圈，罗盘 + 地图朝向给出粗航向，然后直接走（和采集页「标签自动定起点」相同，`9572433`）。

### L3 一键校准（可选，强烈建议）

用户主动给一个「人一定在这一小块」的观测，权重最高：

| 方式 | 精度 | 现状 | 说明 |
|---|---|---|---|
| 摄像头读货架立柱黄色位置标签（如 `082-20`） | 一段货架（约 1～2 m） | 已有 `ShelfSignReader`（Vision OCR，只留「三位-两位」格式，不存图） | 原生 App 可用；网页端 OCR 太重，不做 |
| 扫二维码（贴在黄标签旁或入口） | 一段货架 / 入口点 | **没有**，需要场地打印贴纸 | 所有平台都能扫；入口二维码同时是网页版的入口 |
| 手机贴近任意标签 2 秒 | 0.5 m 内 | 已有 | 只要求 BLE，RSSI 极强即判定 |
| 长按地图「我在这里」 | 取决于用户 | 已有 | 所有平台兜底 |

二维码内容建议：`场地编码 + 位置码（与黄标签同一套编码）`，例如 `https://<域名>/s/<store>?at=082-20`。手机相机直接扫开网页，或在 App 内扫码后直接校准。具体域名和格式待定。

### L4 增强（可选，默认关）

- **地磁指纹**：只在「已经由标签定到、且这片区域有磁场图」时作为额外似然，提升通道内纵向精度；冷启动不用它找位置。需要逐个场地采集，且要先解决跨会话整体偏移（云端已做会话偏移对齐和混合模式，`docs/roadmap.md`）。
- **ARKit / ARCore 视觉里程计**：设备支持且用户愿意举着手机时，替代计步作为运动模型（漂移约行程 1% 量级，`docs/sensor-audit-and-options.md` B1）。房间级实测视觉位姿偏差 0.1～0.6 m（`c71987f`）。耗电发热、需要摄像头朝前，因此只作为「高精度模式」开关。

## 4. 各平台支持

### 4.1 能力矩阵

| 能力 | iOS 原生 App | Android 原生 App | 微信小程序 | 网页（浏览器） |
|---|---|---|---|---|
| 加速度 / 陀螺（L1） | ✅ CoreMotion，50 Hz | ✅ SensorManager | ✅ `wx.startDeviceMotionListening` / `wx.startGyroscope` [待核实频率] | ✅ `DeviceMotionEvent`；iOS 需用户点按授权，且必须 HTTPS |
| 标签 BLE 扫描（L2） | ✅ CoreBluetooth 前台扫描，`AllowDuplicates` 得到连续 RSSI | ✅ BLE Scanner，`SCAN_MODE_LOW_LATENCY` | ⚠️ `wx.startBluetoothDevicesDiscovery` 返回厂商数据和 RSSI [待核实：iOS 端回调频率与去重行为] | ❌ Web Bluetooth 的扫描接口（`requestLEScan`）仍是实验特性，Safari 完全没有 Web Bluetooth |
| 扫黄标签 OCR（L3） | ✅ Vision，本机 | ✅ ML Kit 文字识别，本机 | ⚠️ 需自带模型，体积和速度 [待核实] | ❌ 不做（WASM OCR 太重） |
| 扫二维码（L3） | ✅ | ✅ | ✅ `wx.scanCode` | ✅ 系统相机扫码打开；页内扫码可用 `BarcodeDetector`（Chrome 安卓）或 JS 解码库 |
| 贴标签（L3） | ✅ | ✅ | ⚠️ 同 BLE | ❌ |
| 磁力计（L4） | ✅ | ✅ | ⚠️ 只有罗盘角度，没有原始三轴 [待核实] | ❌ 实际不可用（Magnetometer 接口在实验标志后） |
| AR 视觉里程计（L4） | ✅ ARKit（A12 以上） | ⚠️ ARCore，仅认证机型 | ❌ | ❌ WebXR 只在部分安卓浏览器，iOS Safari 不支持 |
| 后台定位 | 不需要 | 不需要 | 不需要 | 不需要 |

标 [待核实] 的条目我没有在真机上验证，只是根据公开文档的理解，上线前要逐项测。

### 4.2 iOS

- **权限**：蓝牙（`NSBluetoothAlwaysUsageDescription`），运动与健身（CoreMotion 计步，可选），相机（扫码 / OCR 时才请求）。不需要定位权限：标签是厂商数据广播，不是 iBeacon，CoreBluetooth 直接能收到。
- **限制**：后台扫描会合并重复广播、频率大降，所以导航只保证前台。屏幕常亮（导航时禁止自动锁屏）。
- **兼容**：iOS 16 起（和现有 App 一致）。所有 iPhone 都有陀螺和 BLE，L1+L2 不挑机型。

### 4.3 Android

- **权限**：Android 12 起 `BLUETOOTH_SCAN`，声明 `neverForLocation` 可以不要定位权限；Android 11 及以下必须要 `ACCESS_FINE_LOCATION` **并且系统定位开关打开**，否则扫不到任何设备，需要引导。现有采集 App 同时申请了两者。
- **扫描节流**：系统限制 30 秒内最多启动 5 次扫描，所以只开一次长扫描，不要反复开关。
- **机型差异**：RSSI 偏移、扫描回调频率、陀螺质量都比 iOS 分散。用盲标定处理 RSSI；回调频率低于每秒 1 次的机型标为「低精度」。部分国产系统会在省电模式下限制扫描，需提示关闭。
- **无陀螺的低端机**：只能靠加速度计步 + 罗盘航向，精度明显下降，只显示「标签粗定位」。

### 4.4 微信小程序（备选渠道）

对中国场地，小程序是「不用下载 App 又能扫 BLE」的唯一渠道，值得做技术验证。定位核心需要用 JS/TS 重写或编译成 WASM。BLE 回调频率、iOS 上是否能拿到全部标签广播是最大的未知，**先做 1 周验证再决定是否投入**。

### 4.5 网页（最低保障）

- 能做：入口或货架二维码扫开网页 → 位置已知 → PDR + 地图约束跟踪 → 路线导航 → 随时再扫一个二维码重新校准。
- 不能做：BLE 标签、黄标签 OCR、磁力计、AR。因此**没有自动纠偏**，PDR 漂移会累积，走得越远越不准。
- 定位：网页版是「找到这个商品在哪一排 + 大致路线」，不是精确跟踪。界面上要说清楚：「每到一个路口扫一下货架上的码可以更准」。
- iOS Safari 的运动传感器权限必须由用户点按触发，进入导航的按钮兼做授权按钮。

## 5. 精度证据（已有数据，没有新实验）

| 结果 | 数字 | 出处 | 对本设计意味着什么 |
|---|---|---|---|
| 只用标签位置表的蓝牙粗定位 | 中位 1.6～3.4 m，P90 3.2～6.4 m | `docs/roadmap.md`「标签位置表」 | L2 不用采集就能达到 2～3 m 量级 |
| 采集页标签自动定起点（离线回放） | 中位 1.4～2.3 m | 提交 `9572433` | 冷启动可以靠标签，不需要用户操作 |
| 采集学到的标签位置 | 中位 2.5～3.7 m | `docs/roadmap.md` | 表比学的更准，不需要逐个场地采指纹 |
| 跨会话测试加位置表 | 首次定位 33 → 6.5 m，中位 4.2 → 2.6 m | `docs/roadmap.md` | 标签是主要的绝对校正源 |
| `BLEAssist` 交叉检验 | 「自信地定错」少 50%～89%，跳点 6 → 1～3 次 | `docs/roadmap.md` 阶段 3 | 标签能把错误锁定拉回来 |
| 标签名单覆盖 | 实测采到的标签 99.7% 在名单里；371 个采过的标签里 20 个和表差 > 10 m | `docs/roadmap.md` | 位置表大体可靠，但要持续核对 |
| 地磁跨会话 | 中位 3～8 m；整体水平差 10～16 µT，大于磁场起伏（σ 2.4 µT） | `docs/roadmap.md` 2026-10-07 | 地磁不能当主干 |
| 公开商场数据，冷启动只磁场 | 错定 96%（ms）/ 96%（mloc） | `docs/benchmark.md` | 同上 |
| 公开数据，已知起点纯推算（合成漂移） | 中位 27 cm / P90 148 cm（ms），65 / 535 cm（mloc） | `docs/benchmark.md` | 起点准时，短时 PDR 可用；位姿是合成的，偏乐观 |
| ARKit 房间视觉位姿 | 偏 0.1～0.6 m | 提交 `c71987f` | L4 的上限，不是顾客默认能拿到的 |

**还没有的证据（上线前必须补）**：

1. **真机「只用 PDR + 标签 + 通道约束、不开 ARKit」的整段定位精度**。以上标签数字是定起点或粗定位，不是连续跟踪；现有回放都带 ARKit 或合成位姿。
2. **安卓多机型的标签 RSSI 和回调频率**。目前只有 参考机（采集）和 带 LiDAR 的 iPhone。
3. **手持姿态变化、推车、人多时的计步误差**。
4. 小程序和网页的传感器实际表现。

## 6. 精度目标与界面档位

| 档位 | 条件 | 目标（中位 / P90） | 界面表现 |
|---|---|---|---|
| A 精确 | L1+L2，近 10 秒有标签观测，且交叉检验一致 | ≤ 2 m / ≤ 4 m，能分清通道 | 蓝点 + 小圈，逐段转向提示 |
| B 区域 | L1+L2 但标签少或不一致 | ≤ 4 m / ≤ 8 m | 大圈，提示「在 X 区附近」 |
| C 推算 | 只有 L1（网页版、或扫描被系统限制） | 校准后 30 m 内 ≤ 3 m，之后递增 | 圈随距离变大，提示扫码 |
| 定位中 | 冷启动未收敛或交叉检验失败 | — | 不显示蓝点，只显示目标货架和「站着别动几秒 / 扫一下附近的码」 |

目标数字是预期，第 7 节阶段 1 实测后校准。原则不变：**宁可显示「定位中」，也不显示一个自信的错位置**。

## 7. 上线计划

每个阶段有明确的通过门槛，不过门槛不进下一阶段。

| 阶段 | 内容 | 产出 | 通过门槛 |
|---|---|---|---|
| **0 补证据**（约 1 周） | 用现有 iPhone App 新增「顾客模式」开关：关 ARKit、关地磁，只留 PDR + 标签 + 通道约束；在 F1 场地走 5 段测试会话；`hpass-eval` 增加同样的模式离线回放 | 精度报告 | 中位 ≤ 2.5 m，P90 ≤ 5 m，错定（> 5 m）≤ 5% |
| **1 定位核心抽离**（约 1～2 周） | 把 L1/L2/L3 的逻辑整理成平台无关的观测接口；回放测试覆盖各种降级组合 | `HPASSKit` 顾客模式 API | 回放结果和阶段 0 一致 |
| **2 iOS 顾客 App 试点**（约 2 周） | 找货（SKU / 名称 / 条码）→ 定位 → 导航；L3 黄标签 OCR、贴标签、长按；精度档位界面 | TestFlight / Ad Hoc（已有 `ios-adhoc.yml`） | 一家店、10 名员工各完成 10 次找货，到达率 ≥ 90%，平均用时比不用 App 短 |
| **3 Android 顾客 App**（约 3 周） | 移植定位核心（Kotlin）；权限引导（定位开关、省电模式）；机型默认 RSSI 偏移表 | APK | 至少 5 款主流机型过阶段 0 的门槛（可放宽到 P90 ≤ 6 m） |
| **4 二维码贴纸 + 网页版**（约 2 周，可与 3 并行） | 场地打印入口和每排货架二维码；网页版：扫码定位 + PDR + 导航 | 网页 + 贴纸模板 | 扫码后 30 m 内到达正确货架 ≥ 80% |
| **5 小程序验证**（约 1 周，可选） | 只验证 BLE 扫描回调与传感器频率 | 结论文档 | 两端都能每秒收到 ≥ 1 次大部分附近标签 → 决定是否开发 |
| **6 多店推广** | 每店只需：地图 JSON + 标签位置表（场地系统导出）+ 地图朝向（云端估）；可选贴二维码；不需要采集 | 上线清单 | 新店上线不需要到店采集 |
| **7 增强（按需）** | 高客流场地补采地磁图；支持 AR 的手机提供「高精度模式」 | — | A/B 对比确有收益才默认开 |

运营配套：

- **标签位置表的维护**：标签挪位后表会过时。利用顾客端（匿名、只上报标签 ID 和估计位置偏差，不上报轨迹）或员工端的「学到的位置和表差 > 10 m」报告，定期发给场地核对。是否上报、上报什么需要隐私评审。
- **地图更新**：货架调整后由场地更新地图 JSON，云端重新打包；手机按版本自动更新（已有机制）。

## 8. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 真机 PDR + 标签连续跟踪达不到 2.5 m | 档位 A 名不副实 | 阶段 0 先测；不达标则加强 L3（更多二维码），或把 AR 高精度模式提前 |
| 安卓扫描被系统或省电策略限制 | 退化到档位 C | 权限与省电引导；检测回调频率，低于阈值时如实降档 |
| 标签位置表错误或过时 | 局部被拉偏 | 交叉检验 + 学到的位置覆盖 + 差异上报 |
| 标签广播格式或厂商变更 | L2 失效 | 解析逻辑按场地配置（公司 ID、ID 字节），不写死 |
| 顾客隐私顾虑（蓝牙、相机、运动） | 授权率低 | 只在使用时请求；全部本机计算，不上传轨迹和画面；权限说明写清楚 |
| 推车 / 口袋 / 频繁换手 | 计步失真 | 运动类型检测 → 降档提示；标签频繁校正 |
| 网页版无自动纠偏 | 走远后不准 | 定位为「找排 + 大致路线」，二维码密度足够时每 20～30 m 一个 |

## 9. 不做的事

- 不在场地加装 UWB 或额外信标：标签已经覆盖。
- 不要求顾客做任何标定或采集。
- 顾客端不默认开摄像头做持续视觉定位：耗电、发热、需要举着手机。
- 不上传顾客的轨迹或摄像头画面。
